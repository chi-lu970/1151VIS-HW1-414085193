# HW1 規劃：台灣本島地形高度分佈（D3.js 靜態視覺化）

> 本文件用來鎖定設計決策，避免後續反覆討論需求。若要調整方向，請直接修改本檔案對應段落，
> 而不是重新口頭描述一次。開始寫程式前，先確認下方「待確認事項」沒有問題。

## 1. 作業目標

- 主題：**台灣本島**地形高度分佈（不含澎湖、金門、馬祖等離島）
- 形式：D3.js **靜態視覺化**（無需即時資料、無需複雜互動；可以有極輕量的 hover 提示，但畫面本身要能單獨閱讀）
- 目標：從「空間分布」「地形結構」「統計分布」「人的尺度」四個互補角度，完整呈現台灣地形

## 2. 視覺化組合（設計決策）

採用 **3 個核心視圖 + 1 個選配（原規劃時間允許再做，實作時已全數完成）**，共用同一份地形資料與同一套色階，讓整份作業視覺上是一致的敘事，而不是四張互不相關的圖。每張圖的優缺點與為何選擇該呈現方式，見第 7 節事後檢視。

### View 1（主視覺）分層設色地形圖 Hypsometric Tint Map

- 呈現台灣本島整體地形高度的空間分布，是全作業的核心圖
- 技術：
  - 用 `d3.contours()` 對高程網格資料在多個門檻值（如 0/100/500/1000/1500/2000/2500/3000/3500m）產生等值線，依序由高到低疊圖畫出「填色帶」（每個門檻的 contour 蓋在下一層上面，是 d3-contour 常見的 filled-band 技法）
  - 配色：傳統地形圖分層設色（綠→黃→棕→白），用 `d3.scaleThreshold` 對應上述門檻值，讓讀者一眼辨識平原／丘陵／高山
  - 用台灣海岸線 GeoJSON/TopoJSON 做 `clipPath`，裁掉海面雜訊
  - 附垂直圖例（色帶 + 高度刻度）
- 效能備案：若全島高解析度 SVG 路徑過大導致卡頓，改用 `<canvas>` 逐格上色（同一套色階邏輯，只是渲染层換成 canvas）

### View 2 等高線圖 Contour Line Map

- 呈現山脈的立體結構（中央山脈、雪山山脈、玉山山脈、阿里山山脈、海岸山脈）
- 技術：`d3.contour` 純線稿模式（等高距如 500m），不做填色或用極淡填色
- 標註 3–5 個重要山峰（玉山 3952m、雪山 3886m、合歡山等）作為固定文字標籤（靜態圖，不用 tooltip）
- 獨立面板呈現（不與 View 1 疊圖），避免資訊過密

### View 3 面積—高程分佈直方圖 Area–Elevation Distribution

- 統計視角：回答「台灣有多少比例的土地落在哪個海拔區間」
- 技術：水平長條圖，x 軸為面積佔比（%），y 軸為高程區間
- 高程區間**實作時改用與 View 1 完全相同的門檻**（0/100/500/1000/1500/2000/2500/3000/3500m），
  而非原規劃的均勻 500m 一階。原因：這樣每個長條的顏色跟高度區間，能跟 View 1 圖例逐格對應，
  三張圖共用同一套「門檻 + 色彩」語彙，讀者看完 View 1 的圖例後不需要重新學一套新的分級
  （代價：0–100m 這格特別窄、跟其他格距不等寬，統計上不是均勻分箱，但可讀性優先於統計慣例）
- 每個長條的顏色沿用 View 1 的分層設色，讓三張圖之間有視覺連結
- 選配加值：疊加一條累積曲線（hypsometric curve，地形學經典圖），非必要但可加分（**未實作**，見第 8 節）

### View 4（選配 / 時間允許再做）剖面圖 Elevation Profile —— 已實作 ✅

- 沿一條穿越台灣的線畫出海拔剖面。實作採**固定緯度北緯 23.47°**（通過玉山）的東西向剖線，
  而非原規劃的南北向或中橫公路路線，理由：東西向切過中央山脈只需一條緯線，用
  `sampleElevation()` 對顯示網格做雙線性內插即可逐點取樣，不需額外準備一條任意路線的座標序列
  （南北向或中橫公路路線需要手動描出一串轉折點，複雜度高出許多，且非核心必要）
- 技術：`d3.area` + `d3.line`，x 軸為沿線距離（km，用該緯度的 cos 值換算經度差為公里），
  y 軸為海拔；海洋／離島取樣點（nodata）一律視為海平面 0m，讓剖面自然呈現「西岸 → 爬升 → 東岸」
  的完整橫切輪廓，不需要另外裁切陸地範圍
- 面積填色改用垂直漸層，門檻與色彩沿用 View 1／View 3 同一套 `ELEVATION_THRESHOLDS` /
  `HYPSOMETRIC_COLORS`，讓四張圖共用同一套視覺語言
- 標註剖線最高點（動態算出，非寫死數字）與東西岸文字
- 提供「人的尺度」視角，與前三張的「地圖俯視」視角互補

## 3. 資料規劃（已實作，狀態：完成 ✅）

### 3.1 來源（已確認可用）

- **地形高程（DEM）**：Copernicus GLO-30 DEM（30m 解析度），來自 AWS Open Data Registry
  公開 S3 bucket `copernicus-dem-30m`（免金鑰、免登入），圖磚命名規則已實測確認：
  `Copernicus_DSM_COG_10_N{lat}_00_E{lon}_00_DEM/....tif`
  下載範圍：緯度 N21–N25、經度 E120–E122（1 度圖磚），涵蓋台灣本島全境，共取得 11 張圖磚（3 張海上圖磚不存在，屬預期）
- **本島邊界**：不另外抓外部邊界檔，改用 DEM 本身推導 —— 對降採樣後的網格用「高度 > 0」判定陸地，再用連通元件分析（`scipy.ndimage.label`）取面積最大的連通區塊 = 台灣本島，自動排除澎湖、金門、馬祖等離島

### 3.2 前處理（Python，一次性離線處理，不在瀏覽器端跑）— 已完成

腳本位於 `hw1/scripts/`，用 `rasterio` / `numpy` / `scipy`：

1. `fetch_dem.py`：下載覆蓋台灣本島的 Copernicus GLO-30 圖磚到 `hw1/data/raw/`（不進 git，見 `.gitignore`）
2. `process_dem.py`：
   - 用 `rasterio.merge` 拼接圖磚，裁切到本島 bounding box（lon 120.0–122.05, lat 21.7–25.4）
   - 降採樣到「統計解析度」網格（1300×1000，約 170m/px），做陸地遮罩 + 連通元件抓本島
   - 用本島遮罩內像元，依緯度校正像元面積（經度方向乘 cos(lat)），算出各高程區間（每 500m 一階）佔本島面積百分比 → `elevation-bands.json`
   - 再降採樣到「顯示解析度」網格（260×200，給 `d3.contour` 用），海洋/離島像元填 `nodata = -9999` → `taiwan-dem-grid.json`
   - 順便輸出摘要統計 → `summary.json`

實測結果（可能因解析度/降採樣略有失真，僅供參考）：本島面積約 39,043 km²（實際約 36,000 km²，高估約 8%，屬本次簡化流程的已知誤差）、最高點約 3819m（降採樣平均使玉山 3952m 略被削低，屬預期現象）、平均海拔約 780m。

## 7. 呈現方式選擇：優缺點與取捨（事後檢視）

> 本節在四張圖都做完、實際看過渲染結果之後回頭補寫，記錄「為什麼是這個呈現方式」「捨棄了什麼」，
> 而不是重講一次技術做法（技術做法見第 2 節）。

### 7.1 為什麼是「四張圖」而不是一張複合圖

最早也考慮過把等高線疊在分層設色地圖上做成一張「終極地形圖」，但捨棄了，原因：

- 三種資訊（色塊分布 / 稜線結構 / 面積統計）疊在一張圖上，視覺密度太高，色塊本身已經用掉了
  「顏色」這個視覺通道，再疊等高線容易讓山脊線被色塊蓋掉、或線稿把色塊弄髒，兩者互相干擾
- 拆開成獨立面板，每張圖可以各自把「一個問題回答清楚」：View 1 回答「哪裡高哪裡低」、
  View 2 回答「山脈怎麼連起來、稜線走向」、View 3 回答「多少比例的地在哪個高度」、
  View 4 回答「實際走過去要爬多高」
- 代價：讀者要自己在四張圖之間做心智對照，不像一張複合圖資訊「一次到位」。用共用色階
  （`ELEVATION_THRESHOLDS` / `HYPSOMETRIC_COLORS`，定義在 `main.js`，四張圖都讀同一份）
  降低這個代價——同一個顏色在四張圖裡永遠代表同一個高度區間

### 7.2 View 1 分層設色地形圖（Hypsometric Tint Map）

- **優點**：傳統地形圖語彙（綠→黃→棕→白＝低→高），不需要額外學習就能讀懂空間分布；
  作為全作業的「主圖」，一眼就能建立「台灣中央是山、東西兩側是平原/丘陵」的整體印象，
  適合放在最前面當作敘事起點
- **缺點**：`d3.scaleThreshold` 把連續的高程資料切成 9 個離散色階，同一色帶內看不出漸變
  （例如 1500–2000m 之間到底是靠近 1500 還是靠近 2000，圖上分不出來）；對色弱使用者，
  綠—黃—棕這組漸層在部分色弱類型下對比會下降，是已知取捨但未特別做色弱替代色階
- **為何選擇（而非用連續漸層 `d3.scaleSequential`）**：分層設色是地形圖領域的慣例讀法，
  讀者（含助教）大機率已經看過類似圖，比起連續漸層更容易在幾秒內定位「這是平原還是高山」；
  連續漸層雖然資訊保真度更高，但需要對照色標才能讀出精確數值，不適合這種「先求整體印象」
  的主圖定位

### 7.3 View 2 等高線圖（Contour Line Map）

- **優點**：只用線條就能表現稜線走向與山脈的分支結構，是地形學的標準呈現法；不上色能讓視覺
  焦點完全落在「線條疏密＝坡度陡緩」這件事上，疏的地方平緩、密的地方陡峭，一眼就能比較
  中央山脈跟海岸山脈的坡度差異
- **缺點**：對不熟悉等高線讀法的讀者，單看線條較難直接感受「立體感」，需要搭配文字說明或
  先看過 View 1 建立顏色→高度的對應，才比較容易理解等高線圖在講什麼；高峰標註位置是手動
  校正的概略座標（`NAMED_PEAKS` 註解已註明），不是精測點，只做示意
- **為何獨立成一個面板（不疊在 View 1 上）**：見 7.1；改用淡底色（`#f0ede6`）取代分層設色，
  只留陸地輪廓當參考，讓等高線本身的疏密節奏不被色塊的視覺重量蓋過

### 7.4 View 3 面積—高程分佈直方圖（Area–Elevation Distribution）

- **優點**：把「地圖」轉成「統計量」，直接回答 View 1／View 2 兩張空間圖都無法回答的問題——
  「這些高度各自佔了多少比例的土地」；長條圖對「比大小、比排序」是最容易讀的圖表形式之一，
  例如一眼就能看出 0–100m + 100–500m 兩格加起來超過本島一半面積，這件事用地圖很難直接讀出來
- **缺點**：完全失去空間位置資訊——只知道「有 28.4% 的地在 0–100m」，但看不出這些地在西部
  平原還是東部縱谷，必須跟 View 1 對照著看才有完整意義；另外採用跟 View 1 相同但不等寬的門檻
  （見第 2 節 View 3 說明），嚴格統計上不是均勻分箱，犧牲了「箱寬相等」換取「跟 View 1 圖例
  逐格對應」的可讀性，這是刻意的取捨
- **為何選擇水平長條圖（而非圓餅圖或直方圖搭配連續 x 軸）**：長條圖能清楚呈現「由低到高排序」
  且方便標數值標籤；圓餅圖在類別數量到 9 類時已經很難比較切片大小，長條圖在這點明顯更清楚

### 7.5 View 4 剖面圖（Elevation Profile）—— 選配

- **優點**：前三張圖都是「往下看」的俯視視角，View 4 換成「往前看」的人的尺度，用實際爬升
  高度取代抽象的顏色/線條/長條，對「翻越中央山脈實際上要爬多高」這種直覺特別有效；同時用了
  跟 View 1／View 3 相同的色階當作剖面填色，維持整份作業的視覺一致性
- **缺點**：這是**單一路線**的切面，只代表北緯 23.47° 這一條線，不能代表全島地形（例如沒切到
  雪山山脈、南湖大山一帶），剖線位置的選擇本身帶有主觀性；圖上刻意標「玉山一帶」而非直接寫
  死「玉山」，因為緯線剖面取樣點不等於玉山三角點精確座標，實際抓到的最高值跟玉山真實標高
  （3952m）會有落差（見 3.2 節降採樣造成的削低現象），標題用「一帶」避免文字上的過度宣稱
- **為何仍納入（雖然是選配）**：三個核心圖之外多一個互補視角的邊際成本不高（可重用同一份
  `taiwan-dem-grid.json` 跟共用色階），但能明顯補足「地圖看不出坡度陡峭程度的真實感受」這塊，
  值得做；沒有實作原規劃的南北向路線或中橫公路路線，也沒有實作 hypsometric curve 累積曲線
  （原 View 3 的選配加值），是時間/複雜度取捨下明確捨棄的部分，非遺漏

### 7.6 共用設計決策的取捨

- **固定的 9 個高程門檻**（0/100/500/1000/1500/2000/2500/3000/3500m）貫穿四張圖：優點是
  四張圖的顏色語言完全一致，讀者只需要學一次；缺點是這組門檻是人工選定、不是根據資料分布
  （如分位數）算出來的「最優」切分，換一組門檻可能讓某些圖表現得更清楚，但會犧牲跨圖一致性，
  這裡優先選擇一致性
- **用顯示解析度網格（260×200，約每格 850m）畫等值線與剖面，而非原始 30m DEM**：優點是瀏覽器
  端不需要處理百萬級頂點的路徑，渲染快、檔案小；缺點是山峰高度會被降採樣平均削低（玉山網格
  上約 3819–3952m 之間浮動，視取樣點而定），細部地形（例如小型溪谷）在這個解析度下看不出來，
  這是「靜態總覽圖」定位下可接受的犧牲，若要做「可以放大看細節」的圖就不適用這個解法
